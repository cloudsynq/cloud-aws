Lab — Get an Email When Your Server Gets Busy

CloudWatch Alarm + SNS Notification + CloudTrail Audit Trail

Time45–60 minutes
CostFree tier
You needAWS account + a key pair

1. What You Are Building

You will set up a server that emails you by itself when its CPU gets busy. Then you will make the CPU busy on purpose and watch the email arrive.

2. Part 1 — Create the SNS Topic

Build the notification channel first. An alarm needs somewhere to send its message.

1

Create a topic

In the AWS Console, search for SNS → open it → click Topics → Create topic.

  • Type: Standard
  • Name: MyAlertTopic
  • Leave everything else as it is → Create topic
SNS → Topics → Create topic
Screenshot 1 — the topic page after it is created
2

Subscribe your email address

On the topic page click Create subscription.

  • Protocol: Email
  • Endpoint: your own email address
  • Click Create subscription

The status will show Pending confirmation. That is expected — move to the next step.

3

Confirm the subscription — do not skip this

Open your email inbox. You will have a mail from AWS Notifications. Click the Confirm subscription link inside it.

Go back to the AWS console, refresh the subscriptions list, and check the status now reads Confirmed.

Screenshot 2 — the subscription showing status Confirmed
If you skip step 3, the whole lab will fail An unconfirmed subscription receives nothing. The alarm will turn red correctly but no email will ever arrive, and you will think the alarm is broken. Check your spam folder if the confirmation mail is not in the inbox.

3. Part 2 — Launch the EC2 Instance

4

Launch a server

Go to EC2 → Instances → Launch instances.

  • Name: MonitorDemo
  • Image (AMI): Amazon Linux 2023
  • Instance type: t2.micro (free tier eligible)
  • Key pair: select the one you created earlier
  • Network settings: Allow SSH traffic → tick it
EC2 → Instances → Launch instances
5

Turn on Detailed monitoring — important

Before you click Launch, scroll down and expand Advanced details. Find Detailed CloudWatch monitoring and set it to Enable.

Why: normally CloudWatch takes a reading every 5 minutes. With detailed monitoring it reads every 1 minute, so your alarm reacts in 2–3 minutes instead of 10–15. Now click Launch instance.

Screenshot 3 — Detailed CloudWatch monitoring set to Enable
6

Wait for the instance to be ready

Open Instances and wait until Instance state = Running and Status check = 2/2 checks passed. This takes 2–3 minutes.

Note down the Instance ID — you need it in the next part. It looks like i-0a1b2c3d4e5f.

4. Part 3 — Create the CloudWatch Alarm

7

Start a new alarm

Search for CloudWatch → in the left menu click Alarms → All alarms → Create alarm.

Click Select metric.

CloudWatch → Alarms → Create alarm
8

Pick the CPU metric of your instance

In the metric browser: click EC2 → Per-Instance Metrics. A long list appears.

Use the search box and paste your Instance ID. Then tick the row where the metric name is CPUUtilization → click Select metric.

Screenshot 4 — the CPUUtilization row selected for your instance
9

Set the condition

On the Specify metric and conditions page:

  • Statistic: Average
  • Period: 1 minute
  • Threshold type: Static
  • Whenever CPUUtilization is… Greater than 30

Expand Additional configuration and set Datapoints to alarm to 1 out of 1. Click Next.

10

Connect it to your SNS topic

On the Configure actions page:

  • Alarm state trigger: In alarm
  • Send notification to: Select an existing SNS topic
  • Choose MyAlertTopic

Click Next.

11

Name it and create

Alarm name: HighCPUAlarm → Next → review → Create alarm.

Open the alarm. Within a minute or two its state should settle on OK, because an idle server uses almost no CPU.

Screenshot 5 — the alarm showing state OK
If the state says INSUFFICIENT_DATA This is normal for the first few minutes — CloudWatch has not collected enough readings yet. Wait 2–3 minutes and refresh. It will move to OK on its own.

5. Part 4 — Make the CPU Busy and Watch It Fire

12

Connect to the instance

EC2 → Instances → select MonitorDemo → click Connect → choose EC2 Instance Connect → Connect. A terminal opens in your browser.

(If you prefer, SSH in from your own terminal using your key pair — either way works.)

13

Start the CPU load

Type the command below and press Enter. It starts one busy loop for every CPU core, which pushes CPU usage to 100%. Nothing needs to be installed.

Run on the EC2 instance — start the load
# one busy loop per CPU core for i in $(seq 1 $(nproc)); do yes > /dev/null & done

Nothing will be printed. That is correct — the loops are running silently in the background.

14

Watch the alarm turn red

Go back to CloudWatch → Alarms. Keep refreshing. Within 2–3 minutes the state changes from OK to In alarm and the row turns red.

Click the alarm and look at the graph — you can see the exact point where the line crossed the dashed threshold.

Screenshot 6 — the alarm In alarm, with the graph above the threshold
15

Check your email

Open your inbox. There is a mail from AWS Notifications with the subject starting “ALARM: HighCPUAlarm…”

Read it — it tells you which metric fired, what the threshold was, and the value that breached it.

Screenshot 7 — the alarm email in your inbox
Checkpoint Your server just told you it was in trouble, by itself, without you watching it. That is the whole point of monitoring.
16

Stop the load and watch it recover

Back in the EC2 terminal, run the command below. A few minutes later the alarm returns to OK on its own — nobody has to reset it.

Run on the EC2 instance — stop the load
# kill all the busy loops pkill yes

6. Part 5 — Find Yourself in CloudTrail

You did not set up CloudTrail. It has been recording all along. Now go and read what it saw.

17

Open Event history

Search for CloudTrail → in the left menu click Event history.

You will see a list of every action you have taken in this account recently.

CloudTrail → Event history
18

Find the moment you launched the instance

In the filter box choose Event name and type RunInstances. Press Enter, then click the event in the results to expand it.

Read these fields and write them in the table below:

  • User name — who did it
  • Event time — when
  • Source IP address — the internet address you were sitting at
  • Resource type / name — what was affected
Screenshot 8 — the expanded RunInstances event
Think about this CloudTrail recorded your IP address and your username the moment you clicked Launch — without anyone configuring it. This is why CloudTrail is the answer whenever a question asks “who did this?”

8. If Something Does Not Work

Problem Reason Fix
Alarm turned red but no email arrived The email subscription was never confirmed SNS → Topics → your topic → check status is Confirmed. Check spam folder for the confirmation mail.
No confirmation email at all Wrong address typed, or it went to spam Delete the subscription and create it again, carefully. Check spam and promotions folders.
Alarm stuck on INSUFFICIENT_DATA Not enough readings collected yet Wait 3–5 minutes. If it stays there, confirm the instance is Running and that you picked the right Instance ID.
Alarm never turns red even though CPU is loaded The metric belongs to a different instance Delete the alarm, create it again, and search by your exact Instance ID when selecting the metric.
Alarm takes more than 10 minutes Detailed monitoring was not enabled, so readings come every 5 minutes EC2 → select instance → Monitoring tab → Manage detailed monitoring → Enable
nproc or yes command not found You are on a Windows instance, not Linux This lab needs Amazon Linux 2023. Launch a Linux instance.
Cannot connect with EC2 Instance Connect SSH (port 22) is not allowed in the security group EC2 → Security tab → security group → Edit inbound rules → allow SSH / port 22
CPU goes back down on its own Your terminal session closed, which killed the loops Reconnect and run the load command again

9. Clean Up — Do Not Skip This

Leaving resources running will use up your free tier. Delete them in this order:

OrderWhatWhere
1Terminate the EC2 instanceEC2 → Instances → select → Instance state → Terminate instance
2Delete the alarmCloudWatch → Alarms → select HighCPUAlarm → Actions → Delete
3Delete the SNS topicSNS → Topics → select MyAlertTopic → Delete
Leave CloudTrail alone There is nothing to delete for CloudTrail — Event history is a built-in feature, not something you created. It costs nothing.
