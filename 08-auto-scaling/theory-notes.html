AWS · Module 09

Auto Scaling Groups

Theory Notes — Launch Templates, Scaling Policies and Self-Healing

1. What the Load Balancer Did Not Solve

In the last topic you built a load balancer with two servers behind it. Traffic gets shared, and if one server dies the other carries on. That is a real improvement.

But notice what is still fixed: the number two. You chose it, and it never changes. Nobody is adding a third server when things get busy, and nobody is shutting one down at 2 a.m.

Real situation — a food delivery app

Traffic is almost nothing from 2 a.m. to 7 a.m. It climbs through the day and explodes between 7 p.m. and 10 p.m. — dinner time.

You have to pick a fixed number of servers. So which number?

Pick enough for dinner time and you are paying for those servers all night while nobody uses them. Pick enough for the night and the app crawls to a stop exactly when every customer is ordering.

There is no right number. That is the problem.

2. What an Auto Scaling Group Is

Definition An Auto Scaling Group (ASG) is a service that automatically adds EC2 instances when demand rises and removes them when demand falls, keeping the number of servers matched to the actual load — without anyone watching.
Analogy — a restaurant calling in waiters

A restaurant manager does not keep twenty waiters standing around at 11 a.m. when the place is empty. Two is plenty.

At 8 p.m. the restaurant fills up. The manager phones the extra staff: “come in now.” By 11 p.m. the crowd thins out and she sends most of them home.

She never goes below two — somebody has to be there. And she never calls in more than twenty, because she cannot afford it.

That manager is the Auto Scaling Group. Two is the minimum, twenty is the maximum, and the number working right now is whatever the crowd needs.

Notice something important: Auto Scaling does not make any server bigger or faster. It changes how many servers there are.

ApproachWhat you doAnalogy
Scaling UP
vertical scaling		 Replace the server with a bigger one — t2.micro becomes t2.large Hire one faster clerk. There is a limit to how fast one person can be.
Scaling OUT
horizontal scaling		 Add more servers of the same size Open more billing counters. You can keep opening more.
Remember the words Auto Scaling Groups do horizontal scaling — scaling OUT and IN. Adding servers is called scale out; removing them is scale in. The exam uses these exact words.

3. The Three Numbers That Define an ASG

When you create an Auto Scaling Group, you set exactly three numbers. Everything else is detail. Get these three right and you understand ASGs.

SettingWhat it meansWhat goes wrong if you set it badly
Minimum The fewest instances allowed. ASG will never go below this, even at 3 a.m. Set it to 0 and your site can go completely offline during a quiet period.
Desired How many are running at this moment. ASG raises and lowers this number. Nothing — this is the one that is supposed to change.
Maximum The most instances allowed. ASG will never launch past this. Set it too high and a traffic spike — or an attack — can run up a huge bill.
Why maximum matters more than students expect Maximum is not a performance setting, it is a budget setting. Without it, a bot attack sending millions of fake requests would make Auto Scaling cheerfully launch hundreds of instances — and you would get the bill. Maximum is the line that says “beyond this point, slow down rather than spend more.”

4. The Launch Template — the Blueprint

Here is a question worth pausing on. When Auto Scaling decides to add a server at 3 a.m., what server does it create? Which AMI, which size, which security group, which key pair?

Nobody is awake to tell it. So you have to write it all down in advance. That written-down specification is the Launch Template.

Analogy — the recipe

A restaurant's head chef writes down the recipe for their signature dish: exact ingredients, exact quantities, exact steps.

Now any cook on any shift can produce the identical dish without asking anybody. The chef does not need to be in the kitchen.

A Launch Template is that recipe. Auto Scaling follows it to produce identical servers, at any hour, with nobody supervising.

The Launch Template specifiesExample
AMI — the operating system imageAmazon Linux 2023
Instance typet2.micro
Key pairYour SSH key
Security groupWeb-SG
User data scriptInstall Apache and write the home page
Storage8 GB gp3 volume
Why the user data script suddenly matters so much A brand-new instance launched by Auto Scaling is completely blank. No Apache, no website, nothing. If the user data script does not install and configure everything, the new server comes up useless and fails its health check.

This is why you learned user data back in the EC2 module. With Auto Scaling it stops being a convenience and becomes essential.
You may see an older name Older documentation mentions Launch Configurations. That is the previous generation — it cannot be edited after creation and AWS no longer recommends it. Always use Launch Templates, which support versions so you can update them.

5. How Auto Scaling Knows When to Act

Auto Scaling has no opinion of its own about whether your servers are busy. It has to be told — and it is told by something you already know.

The connection back to Module 08 CloudWatch alarms trigger Auto Scaling. The same alarm you built to send yourself an email can instead tell an Auto Scaling Group to launch another server. Same alarm, different action.

The four kinds of scaling policy

PolicyHow you describe what you wantUse it when
Target tracking
recommended		 “Keep average CPU at 50%.” AWS works out the rest. Almost always. Simplest and hardest to get wrong.
Step scaling “CPU above 60% → add 1. Above 85% → add 3.” You want a bigger reaction to a bigger problem.
Simple scaling “CPU above 70% → add 1, then wait.” Older and slower to react. Rarely the best choice now.
Scheduled scaling “Every weekday at 9 a.m. set desired to 10.” The spike is predictable by the clock, not by the metric.
Real situation — why scheduled scaling exists

Your college opens result downloads at exactly 10 a.m. on a known date. Within thirty seconds, thousands of students hit the site.

Target tracking would react only after CPU climbs — and launching a new instance takes a couple of minutes. For the first few minutes the site would struggle.

So you also add a scheduled action: at 9:45 a.m., set desired capacity to 10. The servers are already warm and waiting before the first student clicks. You scale ahead of a spike you can predict.

Cooldown — why it pauses between actions

Analogy — give the new waiter a minute

The restaurant gets busy and the manager calls in one extra waiter. That waiter takes a few minutes to arrive, tie an apron and start taking orders.

If the manager checked again ten seconds later, the restaurant would still look overwhelmed — so she would call another waiter. And another. Soon fifteen waiters are standing around for a crowd that needed three.

So after calling someone, she waits. That wait is the cooldown.

A new EC2 instance takes a couple of minutes to boot, run its user data script, and pass health checks. During that time the metric has not improved yet. The cooldown period — 300 seconds by default — stops Auto Scaling from over-reacting to a problem it has already fixed.

6. Self-Healing — the Feature Nobody Expects

Auto Scaling is usually explained as “handles traffic spikes”. But the feature companies value most is something else entirely.

The real headline If an instance becomes unhealthy, the Auto Scaling Group terminates it and launches a replacement — automatically. The desired capacity says 3, so it will keep making sure there are 3 healthy instances, forever.
Real situation — the server that nobody fixed

An instance runs out of memory at 2 a.m. and stops responding.

With a plain load balancer, the health check removes it from rotation. The site stays up — but now you are running on two servers instead of three, and somebody has to notice and fix it in the morning.

With an Auto Scaling Group, the broken instance is terminated and replaced with a fresh one within minutes. By morning the system is back at full strength and the only sign anything happened is a line in the activity history.

Two kinds of health check — and this one catches people out

Health check typeWhat it actually checksWhat it misses
EC2
the default		 Is the virtual machine running and reachable? A crashed web server on a perfectly healthy machine
ELB
turn this on		 Is the load balancer's health check passing — is the website actually responding? Nothing important
A gap that looks like a bug By default an Auto Scaling Group uses only the EC2 health check. If Apache crashes but the instance keeps running, the EC2 check still says “healthy” — because the machine is healthy. The website is down, and Auto Scaling does nothing about it.

Fix: when attaching an ASG to a load balancer, turn on ELB health checks. Now the ASG replaces any instance whose website stops responding, not just instances that have crashed outright.

7. Auto Scaling and the Load Balancer Together

Each one alone is only half a solution:

  • A load balancer alone shares traffic — but across a fixed, manually managed set of servers.
  • An ASG alone creates and destroys servers — but users have no single address to reach them at, and the addresses keep changing.

Put together they complete each other. When the ASG launches an instance it automatically registers it into the target group, and when it terminates one it removes it first. You never touch the target group by hand again.

Spreading across zones happens for free If you give the Auto Scaling Group two subnets in two Availability Zones, it balances instances between them on its own. Ask for 4 instances and you get roughly 2 in each zone. If one zone fails, the ASG launches replacements in the surviving zone.
