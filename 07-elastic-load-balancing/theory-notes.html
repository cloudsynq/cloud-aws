Elastic Load Balancing (ELB)

Theory Notes — ALB, NLB, Target Groups and Health Checks

1. Start With the Problem

Until now you have launched one EC2 instance and put a website on it. That works perfectly — until two things happen.

Real situation — university result day

Your college puts the semester results on a website. On a normal day about 100 students visit it. One small server handles that easily.

Result day arrives. 50,000 students open the site in the same ten minutes.

The single server runs out of memory and stops responding. The website is down — for everyone. And it goes down at exactly the moment it matters most.

There are two separate problems hiding in that story:

  1. Too much traffic for one server. One machine has a limit.
  2. One server means one point of failure. If it dies, the whole site dies with it.

Adding more servers alone does not fix this. If you have three servers, users still have to know which one to open. Nobody is going to type server2.college.ac.in because server 1 is busy.

You need something that sits in front of all the servers and sends each visitor to a free one. That something is a Load Balancer.

2. What a Load Balancer Actually Is

Definition A Load Balancer is a service that receives all incoming traffic and distributes it across several backend servers, so that no single server is overloaded and no single server failure can bring the application down.
Analogy — the bank counter manager

You walk into a bank. There are five counters open. You do not walk around checking which clerk looks free — there is a manager standing at the entrance who looks at all five counters and tells you: “Counter 3, please.”

You do not know or care which counter you get. You just want your work done.

Now suppose the clerk at counter 2 goes for tea. The manager simply stops sending people to counter 2 and keeps using the other four. Customers never find out that anything happened.

That manager is the Load Balancer. The counters are your EC2 instances.

In AWS this service is called Elastic Load Balancing, shortened to ELB. “Elastic” means it grows and shrinks by itself as traffic changes — you never have to resize it.

The two things it gives you

Benefit What it means in practice
Scalability Traffic that one server cannot handle gets shared across many servers. Need more capacity? Add another server to the group.
High Availability If a server crashes, the load balancer notices and stops sending traffic to it. The remaining servers carry on. Users see no error.
Real situation — updating a live website

Your website is running on three servers behind a load balancer and you need to install an update.

Without a load balancer you would have to take the site offline, update it, and put it back — users get an error page the whole time.

With a load balancer you remove Server 1 from the group, update it, and add it back. Then Server 2. Then Server 3.

At every moment at least two servers are serving traffic. The website is never down and no user notices the update happening. This is called a rolling update, and it is one of the biggest practical reasons companies use load balancers.

3. The Parts of a Load Balancer

When you create a load balancer in AWS you are really creating four connected things. You will build exactly these in the lab, so learn the names now.

PartWhat it does
Load BalancerThe manager itself. Faces the internet and receives every request.
ListenerSays which port and protocol to accept, for example HTTP on port 80. Without a listener the load balancer accepts nothing.
Target GroupThe list of servers that can receive traffic, plus the health check settings for them.
TargetsThe actual EC2 instances inside the target group.

4. Health Checks — How It Knows a Server Is Dead

A load balancer cannot read your mind. It has no way of knowing that Server 3 crashed at 3 a.m. So it keeps asking.

Analogy — roll call in class

A teacher calls out names every morning. If a student answers “present”, the teacher gives them work. If a student does not answer for several days in a row, the teacher marks them absent and stops giving them work.

The day that student comes back and answers again, the teacher starts giving them work again — automatically, with no special request needed.

That is exactly a health check. The load balancer calls out to every server on a schedule and listens for an answer.

Here is what the load balancer actually does: it sends an HTTP request to a path you choose — by default just / — to every registered target, roughly every 30 seconds.

The server replies withThe load balancer marks itGets traffic?
HTTP 200 OKHealthyYes
An error, or no reply at allUnhealthyNo
Real situation — the 3 a.m. crash

One of your three servers runs out of disk space at 3 a.m. and the web server process dies.

Within about a minute the load balancer's health check fails, that server is pulled out of the target group, and the other two take all the traffic.

You fix it in the morning. No user ever saw an error and nobody had to be woken up.

The most common lab failure If your web server has no page at the health check path, every target becomes unhealthy, and the load balancer has nowhere to send traffic. The browser then shows HTTP 503 — Service Temporarily Unavailable.

So the fix for a 503 is almost always: make sure index.html exists on the instances and the web server is actually running.

5. Types of Load Balancer

AWS gives you more than one kind, because different applications need different things. The difference comes down to how deeply the load balancer looks at your traffic.

Analogy — receptionist vs courier

A receptionist opens your letter, reads what it is about, and decides: “This is a complaint — send it to the complaints department. This is a bill — send it to accounts.” Reading takes a moment, but the letter reaches exactly the right place.

A courier never opens anything. He looks at the address on the sealed envelope and delivers it. He has no idea what is inside — which is why he is extremely fast.

The ALB is the receptionist. The NLB is the courier.

How to choose, in one line If your application speaks HTTP or HTTPS, use an ALB. That covers almost everything you will ever build. Choose NLB only when you need extreme speed or a fixed IP address. Never choose CLB for new work — it is the old generation and AWS recommends moving off it.

Why the ALB being able to "read" matters

Because an ALB understands HTTP, it can look at the URL and send different parts of the same website to different groups of servers. This is called path-based routing.

Real situation — an online shop

Image files are heavy but simple to serve. Checkout and payment are light on bandwidth but need serious processing. Mobile app requests go to a completely different codebase.

With path-based routing all three live under one domain and one load balancer, but run on three independent sets of servers. If the image servers get overwhelmed during a sale, checkout keeps working normally.

6. A Load Balancer Has a Name, Not an IP

When you create a load balancer, AWS does not hand you an IP address. It gives you a DNS name that looks like this:

What AWS gives you
my-first-alb-1847263910.us-east-1.elb.amazonaws.com

Students always go hunting for the IP address and cannot find one. There is a good reason for that.

Analogy — the shop name board

A famous sweet shop in your city has been running for forty years. In that time it has moved buildings three times — different street, different address each time.

Nobody says “meet me at plot number 47-B.” Everybody says “meet me at Sharma Sweets.” The name stays constant even though the address keeps changing.

A load balancer works the same way. Behind the scenes AWS adds and removes machines as traffic changes, so the underlying IP addresses keep changing. The DNS name never does.

This is why Route 53 exists Your users are not going to type my-first-alb-1847263910.us-east-1.elb.amazonaws.com. You point your real domain — shop.example.com — at that load balancer name using Route 53, which is the next topic in this module.

7. Security Groups — Two Layers, Not One

Once a load balancer sits in front of your servers, there are now two doors to configure, not one.

Security group onAllow port 80 fromWhy
The load balancer 0.0.0.0/0 — anywhere It is the public front door. Everyone must be able to reach it.
The EC2 instances The load balancer's security group The servers should only ever be reached through the load balancer, so nobody can bypass it.
A mistake that still "works" If you open port 80 on the EC2 instances to 0.0.0.0/0, the website will load and everything will look fine — so students assume it is correct.

But now anyone who discovers an instance's public IP can hit that server directly, skipping the load balancer, its health checks and its rules completely. Always point the EC2 rule at the load balancer's security group.

8. Two Availability Zones Are Compulsory

When you create an ALB, AWS forces you to select at least two subnets, in two different Availability Zones. You cannot create it with only one.

Why AWS insists An Availability Zone is a separate physical data centre. If the whole zone loses power and your load balancer existed only there, the load balancer itself would disappear — and a load balancer that can die is useless for high availability. Spreading it across two zones means one data centre can fail completely and your site stays online.
Real situation — the flooded data centre

A company runs everything in us-east-1a. A power failure takes that zone offline. Their servers, and the load balancer in front of them, all go down together.

A second company runs the same application across us-east-1a and us-east-1b. When zone a fails, health checks mark those servers unhealthy and all traffic shifts to zone b within about a minute. Their customers notice nothing.

9. Two More Terms You Will Hear

Sticky sessions

Analogy — the same waiter

You sit down in a restaurant and a waiter takes your order. Twenty minutes later you ask for water — and a completely different waiter arrives who knows nothing about your table or your order.

Annoying. So restaurants keep one waiter assigned to your table for the whole meal.

Some applications store your shopping cart or login session in the memory of one server. If the load balancer sends your next click to a different server, that server has never heard of you — your cart appears empty and you get logged out.

Sticky sessions solve this. The ALB puts a small cookie in your browser so every request from you keeps going back to the same server for as long as the session lasts.

Good to know Sticky sessions are a workaround, not a design goal. A better-built application stores sessions in a shared place — a database or a cache — so that any server can serve any user. You will see this idea again when you study ElastiCache.

Cross-zone load balancing

Suppose zone a has 4 servers and zone b has 1. Should traffic be split 50–50 between the two zones, which would overload that single server, or spread evenly across all 5 servers?

Spreading evenly across every server regardless of zone is called cross-zone load balancing. On an ALB it is always on, so you do not have to think about it. It is simply the reason an ALB distributes traffic so evenly.
