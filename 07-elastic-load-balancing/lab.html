Lab — Build a Load Balancer With Two Servers

Application Load Balancer · Target Groups · Health Checks · Failover Test

Time70–75 minutes
CostFree tier
RegionN. Virginia (us-east-1)

1. What You Are Building read first — 5 min

Two web servers, each showing its own name on a web page. In front of them, an Application Load Balancer. When you refresh the browser, you will see the server name change — proof that your traffic is being spread across both machines.

Then you will deliberately break one server and watch the load balancer notice and route around it.

Before you start Make sure the region selector at the top-right says N. Virginia (us-east-1). Everything in this lab must be in the same region, and we will use the default VPC that already exists in your account — do not create a new VPC.

2. Part 1 — Create Two Security Groups 10 min

You need two: one for the load balancer, one for the servers. Create the load balancer's group first, because the servers' group has to point at it.

1

Create ALB-SG — the public door

EC2 → left menu → Security Groups → Create security group

  • Name: ALB-SG
  • Description: Allows web traffic from the internet
  • VPC: leave the default VPC selected

Under Inbound rules click Add rule:

  • Type: HTTP  (port 80 fills in by itself)
  • Source: Anywhere-IPv4 → 0.0.0.0/0

Click Create security group.

EC2 → Security Groups → Create security group
Screenshot 1 — ALB-SG with its HTTP rule
2

Create Web-SG — the private door

Click Create security group again.

  • Name: Web-SG
  • Description: Allows traffic only from the load balancer

Add two inbound rules:

  • Rule 1 — Type: HTTP · Source: click the search box and select ALB-SG from the dropdown (not an IP address)
  • Rule 2 — Type: SSH · Source: Anywhere-IPv4 — you need this to log in later

Click Create security group.

Screenshot 2 — Web-SG showing ALB-SG as the HTTP source
The single most important step in this lab In rule 1 of Web-SG the source must be ALB-SG, not 0.0.0.0/0. Start typing ALB in the source box and pick the group from the list.

This is what stops anyone from bypassing the load balancer and hitting your servers directly.

3. Part 2 — Launch Two Web Servers 15 min

3

Start the launch wizard

EC2 → Instances → Launch instances

  • Name: WebServer
  • Number of instances: 2 — this launches both in one go
  • Image: Amazon Linux 2023
  • Instance type: t2.micro
  • Key pair: select your existing key pair
4

Attach Web-SG — do not let it create a new one

In Network settings click Edit, then choose Select existing security group and pick Web-SG.

By default the wizard wants to make a brand new security group. If you let it, your servers will have the wrong rules and the lab will fail later.

5

Paste the startup script

Scroll to Advanced details → expand it → scroll right to the bottom to the User data box. Paste the script below.

This script runs automatically the first time each server boots. It installs Apache and writes a page showing that server's own name.

User data — paste this exactly
#!/bin/bash dnf install -y httpd systemctl enable --now httpd echo "<html><body style='font-family:Arial;text-align:center;margin-top:100px'> <h1 style='font-size:44px'>Server: $(hostname -f)</h1> <p style='font-size:20px'>Refresh the page to see the load balancer switch servers</p> </body></html>" > /var/www/html/index.html
Why this script matters $(hostname -f) inserts each server's own private DNS name into the page. Both servers run the same script, but each one produces a different page. Without this you could never tell which server answered you.
6

Launch and wait

Click Launch instance. Two instances appear in the list. Wait until both show Running and 2/2 checks passed — about 3 minutes.

Screenshot 3 — two instances running with 2/2 checks passed
7

Test each server on its own first

Not through the load balancer yet — we have not built it. Copy the Public IPv4 address of instance 1 and open http://<that-ip> in your browser.

It will not load, and that is correct. Web-SG only allows port 80 from the load balancer, so your laptop is blocked. You have just proved your security group works.

Checkpoint A failed page load here is the right answer. If the page does load, your Web-SG has HTTP open to 0.0.0.0/0 — go back and fix rule 1 to point at ALB-SG.

4. Part 3 — Create the Target Group 5 min

8

Create the group

EC2 → left menu, scroll down to Load Balancing → Target Groups → Create target group

  • Target type: Instances
  • Name: web-targets
  • Protocol / Port: HTTP : 80
  • VPC: default VPC
  • Health check path: leave it as /

Click Next.

EC2 → Target Groups → Create target group
9

Register both instances

On the next page, tick both WebServer instances in the list, click Include as pending below, then Create target group.

Open the group and look at the Targets tab. Both will say initial at first, then turn healthy after about a minute.

Screenshot 4 — both targets showing healthy
If they stay unhealthy Wait a full two minutes first — the health check needs several passes. If they are still unhealthy after that, the cause is almost always one of two things: the user data script did not run, or Web-SG is not allowing port 80 from ALB-SG.

5. Part 4 — Create the Load Balancer 10 min

10

Pick the type

EC2 → Load Balancers → Create load balancer → under Application Load Balancer click Create.

EC2 → Load Balancers → Create load balancer → Application Load Balancer
11

Basic settings

  • Name: my-first-alb
  • Scheme: Internet-facing
  • IP address type: IPv4
12

Network mapping — tick two zones

VPC: default VPC. Below it you will see a list of Availability Zones.

Tick at least two, for example us-east-1a and us-east-1b. AWS will not let you continue with only one.

Screenshot 5 — two Availability Zones selected
13

Security group — remove the default one

In the Security groups section, the default group is pre-selected. Remove it by clicking the small × next to it, then select ALB-SG.

Easy to miss If you leave the default security group attached as well, the load balancer may still work — but you are no longer testing the rules you wrote. Make sure only ALB-SG is listed.
14

Listener — connect it to the target group

Under Listeners and routing:

  • Protocol: HTTP · Port: 80
  • Default action: forward to web-targets

Click Create load balancer. It takes 2–4 minutes to become Active.

Screenshot 6 — load balancer state showing Active

6. Part 5 — See It Working 15 min

This is the part the whole lab is for. Do not rush it.

15

Copy the DNS name

Open your load balancer and copy the DNS name from the Details section. It looks like this:

my-first-alb-1847263910.us-east-1.elb.amazonaws.com

Notice there is no IP address anywhere on this page. A load balancer only has a name.

16

Open it in the browser

Paste the DNS name into a new tab with http:// in front. The page loads and shows one of your servers.

Screenshot 7 — the page served through the load balancer
17

Refresh — hard refresh — and watch the name change

Press Ctrl + Shift + R (hard refresh) several times. The server name on the page switches between your two instances.

A normal refresh often shows the cached page, so use the hard refresh.

What you should see, refresh after refresh
Server: ip-172-31-20-15.ec2.internal Server: ip-172-31-45-88.ec2.internal Server: ip-172-31-20-15.ec2.internal Server: ip-172-31-45-88.ec2.internal
This is load balancing One address, two servers, traffic shared between them. Your browser has no idea which machine answered — and it does not need to.

If the name never changes

Your browser may be holding one connection open. Use this instead — connect to either instance (EC2 → Connect → EC2 Instance Connect) and run:

Run on any EC2 instance — replace with your own DNS name
for i in {1..10}; do curl -s http://YOUR-ALB-DNS-NAME | grep Server; done

Ten requests, one after another, with no browser caching in the way. You will see the two server names alternating clearly.

7. Part 6 — Break a Server on Purpose 10 min

Now prove the high-availability claim. You are going to kill one web server while the site is running.

18

Stop Apache on one instance

EC2 → Instances → select the first WebServer → Connect → EC2 Instance Connect → Connect.

In the terminal run the command below. The web server process stops, but the EC2 instance itself keeps running.

Run on WebServer 1 — break it
sudo systemctl stop httpd
19

Watch the target group react

Go to Target Groups → web-targets → Targets tab. Keep refreshing.

Within about a minute that instance changes from healthy to unhealthy, and the reason column says the health check failed.

Screenshot 8 — one target healthy, one unhealthy
20

Check the website — it still works

Go back to your browser tab and hard refresh a few times.

The page still loads every single time. Now it always shows Server 2, because the load balancer has quietly stopped sending anyone to the broken machine.

This is the whole point of the module A server died and not one user saw an error. Nobody got a phone call at night. The site simply kept working with the capacity that was left.
21

Bring it back

In the same terminal, start Apache again. Watch the Targets tab — in about a minute it returns to healthy all by itself, and your refreshes start alternating between both servers again.

You did not have to tell the load balancer anything. The health check figured it out.

Run on WebServer 1 — fix it
sudo systemctl start httpd

9. If Something Does Not Work

What you seeCauseFix
503 Service Temporarily Unavailable Every target is unhealthy, so the ALB has nowhere to send traffic Target Groups → Targets tab → read the health status reason. Usually Apache is not running or Web-SG is wrong.
Page never loads, just spins ALB-SG does not allow port 80 from the internet Check ALB-SG has an inbound HTTP rule with source 0.0.0.0/0
Targets stuck on unhealthy Web-SG does not allow port 80 from ALB-SG Edit Web-SG rule 1 and set the source to the ALB-SG security group, not an IP
Targets unhealthy, Apache is running No index.html, so the health check on / gets a 403 Connect to the instance and run ls /var/www/html. If empty, the user data did not run — re-create the instance with the script.
Same server name on every refresh Browser caching or a kept-alive connection Hard refresh with Ctrl + Shift + R, try an incognito window, or use the curl loop from Part 5
Cannot create the load balancer Only one Availability Zone was ticked Select at least two zones in Network mapping
Targets stay on "initial" Health checks have not finished their first passes Wait a full two minutes before concluding anything is wrong
DNS name does not resolve The load balancer is still provisioning Wait until its state says Active, then try again

10. Clean Up — In This Order 5 min

Order matters A load balancer is not free tier. Delete it first and delete it today, or it will charge you by the hour. Security groups cannot be deleted until nothing is using them, which is why they come last.
OrderDeleteWhere
1Load balancerEC2 → Load Balancers → select → Actions → Delete
2Target groupEC2 → Target Groups → select → Actions → Delete
3Both EC2 instancesEC2 → Instances → select both → Instance state → Terminate
4Web-SG, then ALB-SGEC2 → Security Groups → delete Web-SG first, then ALB-SG

Web-SG must go before ALB-SG, because Web-SG has a rule that points at ALB-SG. AWS will refuse to delete a group that another group still references.
